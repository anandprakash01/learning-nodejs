# Node.js Enterprise Architecture Patterns

When structuring a scalable Node.js application, developers generally choose between two primary architectural patterns: **Horizontal Slicing** (Layered) and **Vertical Slicing** (Feature-Based).

---

## 1. Layered Architecture (Horizontal Slicing)

_Also known as Controller-Service Architecture or MVC (Model-View-Controller)._

In this traditional approach, the application is organized by **technical role**. Every file of a specific type (e.g., all controllers, all models) is grouped together in a single global folder.

### Directory Structure

```text
📁 src
├── 📁 config
│   └── 📄 db.js
├── 📁 controllers
│   ├── authController.js
│   └── userController.js
├── 📁 routes
│   └── 📄 userRoutes.js
├── 📁 services
│   └── userService.js
└── 📁 models
    └── User.js
```

### The Problem at Scale

As the application grows, this pattern becomes a bottleneck. If you need to add a new "Billing" feature, you must open 4 different folders (`routes`, `controllers`, `services`, `models`) and create a new file in each one. It requires jumping all over the codebase, breaking encapsulation, and increasing merge conflicts in large teams.

---

## 2. Feature-Based Architecture (Vertical Slicing)

_Also known as Domain-Driven Architecture or Modular Architecture._

In this modern enterprise pattern, you abandon global controllers or services. Instead, you create a "Mini-Application" for every single business feature or domain.

### Directory Structure

```text
📁 src
└── 📁 modules (or 📁 features / 📁 domains)
    │
    ├── 📁 auth
    │   ├── auth.controller.js
    │   ├── auth.service.js
    │   └── auth.route.js
    │
    ├── 📁 file
    │   ├── file.controller.js
    │   ├── file.service.js
    │   ├── file.model.js
    │   └── file.route.js
```

### The Physics of the Feature Pattern

1. **Absolute Encapsulation:** Everything required to handle a specific feature lives strictly inside `src/modules/file`. If you delete that folder, the file system feature is completely removed without breaking the rest of the application.
2. **Microservice Readiness:** If the "File" feature starts using too much CPU, you can literally copy the `modules/file` folder, paste it into a brand new repository, and deploy it as an independent Microservice in minutes.
3. **The Strict Rule:** A controller inside `modules/file` is **never** allowed to import a model from `modules/user`. If the File module needs User data, it must ask the `user.service.js` for it. This strictly enforces domain boundaries and prevents spaghetti code.

---

## 3. Naming Conventions: Singular vs. Plural

When implementing a Domain-Driven structure, semantic naming is critical.

- **Plural:** Used for grouping folders that hold many things (containers).
- **Singular:** Used for the specific domain/entity being managed, or for uncountable nouns.

```text
src/
├── middleware/          <-- Singular (uncountable noun)
│   ├── auth.js
│   └── error.js
├── modules/             <-- Plural (a container holding many modules)
│   ├── user/            <-- Singular (represents the "User domain", not "Users")
│   │   ├── user.controller.js
│   │   ├── user.model.js
│   │   └── user.routes.js
│   └── product/         <-- Singular (represents the "Product domain")
│       └── product.controller.js
```

---

## 4. The "Shared" or "Core" Directory (Enterprise Addition)

When using feature-based architecture, you will still have code that doesn't belong to any specific domain but is shared across the entire application (e.g., database connections, custom error classes, global utilities).

These go into a `core` or `shared` folder alongside your `modules` folder:

```text
src/
├── 📁 core
│   ├── 📁 config (db.js, env.js)
│   ├── 📁 errors (AppError.js, globalErrorHandler.js)
│   └── 📁 utils (catchAsync.js, logger.js)
├── 📁 modules
│   ├── user/
│   └── file/
```

---

## 5. Bootstrapping: app.js vs server.js (Enterprise Addition)

In a professional architecture, you must strictly separate your Express configuration from your network initialization.

- **`app.js` (The Application):** This file ONLY configures Express. It applies global middleware (Helmet, CORS, Express JSON), wires up the routes from your `modules` folder, and adds the global error handler. It **does not** listen to a port.
- **`server.js` (The Network/Entrypoint):** This file imports `app.js`. It connects to the database (MongoDB) and _then_ calls `app.listen(port)`. It also catches unhandled Promise rejections and shuts down the server gracefully.

This separation allows you to easily test your Express app using tools like `Supertest` without accidentally starting a real live server port during automated testing.
